## 3. 前端架构

### 3.1 实际技术方案

前端采用 **FastAPI + Jinja2 服务端渲染（SSR）** 架构，纯 JavaScript（无框架）+ CSS Variables 实现，不引入前端构建工具链（Webpack/Vite 等）。

**关键决策原因：**
- 与后端统一 Python 技术栈，降低团队认知负担
- 服务端渲染对 SEO 友好，首屏加载更快
- 无前端构建步骤，开发迭代速度更快
- API 请求通过 httpx 代理转发到后端 8080 端口，避免跨域问题

### 3.3 核心设计决策

| 决策点 | 方案 | 理由 |
|------|------|------|
| 渲染模式 | FastAPI + Jinja2 SSR | 统一 Python 技术栈，无前端构建工具链 |
| 样式方案 | CSS Variables + 手写 CSS | Design Tokens 通过 CSS 自定义属性实现 |
| SSE 消费 | fetch + ReadableStream | 原生 API，支持流式读取和中止控制 |
| Markdown 渲染 | 前端 marked.js | CDN 引入，在浏览器端实时渲染 |
| 路由 | FastAPI 路由 + Jinja2 模板 | 服务端路由，模板继承（base.html） |
| 代理机制 | httpx 代理转发 | /api/v1/proxy/* → {BACKEND_URL}/api/v1/* |

### 4.2 中间件链（实际顺序）

```
请求 → Logger → CORS → ContentSafety → RateLimiter → JWT Auth(按路由) → Router
```

**说明：** JWT 认证不在全局 ASGI 中间件链中，而是通过 FastAPI `Depends(get_current_user)` 在每个需要认证的路由中按需注入。

### 4.3 核心模块设计

#### 4.3.1 用户鉴权流程（实际：用户名+密码）

```
注册:  用户名 + 密码 + 协议勾选 → 校验 → bcrypt哈希密码 → 创建用户 → 签发 JWT → 返回
登录:  用户名 + 密码 + 协议勾选 → 校验 → bcrypt密码验证 → 签发 JWT → 返回
刷新:  Refresh Token → 校验 → 签发新 Access Token → 返回
鉴权:  Authorization: Bearer <token> → JWT解析 → 用户信息注入 Context
```

- Access Token 有效期：24小时
- Refresh Token 有效期：7天
- Token 含：user_id、username、sub、exp、iat、iss
- 密码使用 bcrypt 哈希存储
- 预留手机号验证码方案（相关工具函数和数据结构已就绪），v1.0 暂不实现

#### 4.3.2 流式对话流程

```
1. 鉴权校验 → 限流检查
2. 保存用户消息到 MongoDB
3. 调用 RAGFlow 检索 API → 等待 Top-K 法条
4. LangChain 拼接完整 Prompt 上下文
5. LangChain DeepSeek Chat 流式调用
6. 边接收边转发 SSE 到前端（每个 chunk 直接透传）
7. 流结束后：
   - 保存完整 AI 回复到 MongoDB
   - 记录法条引用关联
   - 更新 Token 消耗统计
```

#### 4.3.3 限流与熔断

```
限流策略: 滑动窗口算法 (内存实现)
  - 每用户每分钟 10 次消息发送
  - 每 IP 每分钟 30 次请求
  - 基于 FastAPI 中间件 + collections.deque 实现

熔断策略:
  - 连续失败 5 次 → 熔断器打开(30s)
  - 半开状态：允许 1 次尝试
  - 成功 → 关闭；失败 → 重新打开
  - 基于 tenacity 库实现

重试策略:
  - 指数退避：1s → 2s → 4s (最多3次)
  - 仅对 5xx 和网络错误重试
  - 4xx 错误不重试
```

### 5.3 内嵌文档 vs 引用策略

| 场景 | 策略 | 说明 |
|------|:---:|------|
| 消息 → 法条引用 | **内嵌** (law_refs 数组) | 法条引用与消息强绑定，内嵌可避免 JOIN，一次查询获取完整数据 |
| 会话 → 消息 | **引用** (session_id) | 消息量可能很大，适合独立存储 |
| 用户 → 会话 | **引用** (user_id) | 用户与会话为典型的一对多关系 |

### 5.4 无缓存架构说明

由于不引入 Redis，以下能力通过 MongoDB 内建机制实现：

| 原缓存场景 | MongoDB 替代方案 |
|------|------|
| 会话缓存 | MongoDB 查询性能足够，无需缓存层；利用索引 + 连接池 |
| 限流计数 | FastAPI 中间件 + 内存 collections.deque（单进程） |
| 短信发送频率限制 | sms_codes 集合查询（利用 phone + created_at 复合索引） |
| Token 黑名单 | 在 JWT payload 中设置短有效期（24h），不做服务端黑名单 |
| 熔断器状态 | 内存变量维护（单进程场景），多进程可通过 MongoDB 读写 |

### 7.3 System Prompt 结构

```
[系统角色]
你是一名专业的AI法律助手，基于权威法律法规为用户提供法律信息参考。
你必须严格基于检索到的真实法条回答问题，不得虚构或编造法律条文。
你没有律师执业资格，你的回答不构成法律意见。

[回答格式要求]
你必须按照以下结构组织回答：
1. **问题分析**：简要分析用户提出的法律问题涉及的法律关系
2. **法律依据**：列出相关的法律法规（必须使用格式 `《法律名称》第X条第Y款`，并引用原文）
3. **建议/结论**：基于法律依据给出初步建议
4. **风险提示**：固定附带以下声明

[法条引用规范]
- 只引用检索结果中实际返回的法条
- 引用格式：《法律全称》第X条第Y款
- 如果检索结果中没有相关法条，请明确告知用户"未检索到相关法条"
- 不得自行编造法律条文、不得虚构条款号

[禁止行为]
- 不得预测判决结果
- 不得提供法律代理建议  
- 不得教唆用户采取违法手段
- 不得回答与法律无关的问题
- 不得提供具体法律文书的起草服务（可以说"建议咨询律师起草"）

[拒答规则]
以下情况直接拒答：
- 涉及危害国家安全、煽动暴力、教唆犯罪
- 要求AI扮演律师或法官角色
- 提问超出法律咨询范畴（如医疗建议、心理咨询）
- 拒答话术："抱歉，您的问题超出了我能回答的范围。建议您咨询相关领域的专业人士。"

[风险提示模板]
---
⚠️ **免责声明**
以上内容仅供参考，不构成法律意见。AI并非律师，回答可能存在误差。
如遇重大法律问题，强烈建议您咨询具有执业资格的律师以获取专业法律建议。
---

[当前对话上下文]
用户问题：{user_query}

[相关法律依据]
{retrieved_laws}

请基于以上信息回答问题。
```

## 8. 安全架构

### 8.1 安全分层

| 层级 | 安全措施 |
|------|------|
| **传输层** | HTTPS 全站；HSTS 头；TLS 1.2+ |
| **接入层** | Nginx 限流（limit_req）；IP 黑名单；WAF 规则（可选） |
| **应用层** | JWT 鉴权；API 限流；输入参数校验；SQL 注入防护（参数化查询）；XSS 过滤 |
| **数据层** | 手机号 AES-256 加密；密码哈希（如有）；数据库连接加密 |
| **基础设施** | 安全组最小权限；SSH 密钥登录；定期漏洞扫描 |

### 8.2 内容安全

```
用户输入 → 敏感词匹配(字典树) → 正则规则 → AI内容审核(可选)
    │            │                  │
    ▼            ▼                  ▼
  放行       拦截+记录日志       人工复核队列

AI回复 → 法条引用真实性校验 → 合规声明完整性检查 → 敏感内容二次过滤
```

### 8.3 数据加密

| 数据 | 加密方式 | 密钥管理 |
|------|------|------|
| 用户手机号 | AES-256-GCM | KMS / 环境变量 |
| JWT Token | HMAC-SHA256 | 环境变量 |
| 用户密码（如有） | bcrypt (cost=12) | - |
| 数据库连接 | TLS + 密码 | 环境变量 / Vault |
| 备份文件 | AES-256 加密后存储 | KMS |
